# ТЗ: рулетка 💎 и приёмка ветки v2.0

## Общие правила работы

- Правила проекта — `CLAUDE.md`, пайплайн — `src/docs/dev-pipeline.md`. Перед работой с
  модулем читать его документацию в `src/docs/<модуль>.md` и обновлять её после правок.
- Ветка под задачу, коммиты в формате `тип(модуль): описание`. Минимальный diff:
  не рефакторить попутно то, о чём не просили.
- TypeScript без `any`. Стили — только Tailwind по Apex UI Kit (`src/docs/apex-ui-kit.md`),
  цвета только через переменные `--apex-*`, суммы 💎 только через `CoinIcon`.
- Данные — Server Actions с валидацией Zod, результат `{ success, data | error }`.
  Клиентский кэш — только через `@/modules/cache`. Мутации с оптимистичным обновлением
  и откатом при ошибке. У страниц с загрузкой — свой `loading.tsx`.
- Перед коммитом: `npx tsc --noEmit`, `npm run lint`, `npm run build`.
- Непонятно или есть два равнозначных решения — спросить до начала, не домысливать.

### Чего делать нельзя

- **Не менять данные в боевой базе.** Никаких `INSERT`, `UPDATE`, `DELETE` ради теста:
  ни транзакций, ни балансов, ни событий, ни отсутствий, ни статусов дней, ни заказов.
- **Особенно не менять даты:** `event_date`, `ranking_date`, `created_at`, календарь
  рабочих дней, праздники, даты отсутствий. На них держатся стрики, зелёные и красные
  дни, месячные топы и соревнования — сдвиг одной даты задним числом ломает расчёт
  у всех сразу и чинится только ручным разбором.
- **Не менять схему БД.** Единственная допустимая миграция — под рулетку, и только
  после согласования со мной. Существующие таблицы, вью, функции и триггеры не трогать.
- **Не запускать инструмент корректировок для проверок** — он меняет реальные начисления.
- Нужны тестовые данные — берём ветку Supabase, в проде ничего не правим.

## Задача 1. Рулетка

Раз в календарный месяц сотрудник может крутить рулетку. Ставка — **весь баланс**,
другого варианта нет; крутить можно при балансе больше нуля.

Колесо из 7 секторов с равными шансами:

| Сектор | Баланс после хода | Шанс |
| --- | --- | ---: |
| ×2 | удваивается | 1/7 ≈ 14% |
| +500 💎 | прибавка | 1/7 ≈ 14% |
| +200 💎 | прибавка | 1/7 ≈ 14% |
| +100 💎 | прибавка | 1/7 ≈ 14% |
| +50 💎 | прибавка | 1/7 ≈ 14% |
| Обнуление | 0 | 2/7 ≈ 29% |

Баланс при входе не списывается — исход применяется к текущему балансу.

**Экономика (для проверки цифр в админке).** Средний результат хода при балансе `B` —
`(6B + 850) / 7`. Точка безразличия 850 💎: ниже неё крутить в среднем выгодно
сотруднику, выше — в среднем теряешь (при 5 000 💎 средняя потеря ≈ 590 💎 за ход).
Если за месяц крутят все, кто может (464 человека, 969 116 💎 на 02.11.2026), система
изымает в среднем около 82 000 💎.

**Реализация**

- Исход определяет только сервер; клиент анимирует уже полученный результат.
- Один ход в месяц гарантируется в БД: уникальный `idempotency_key` вида
  `roulette_<user_id>_<YYYY-MM>`. Повторный запрос, двойной клик и вторая вкладка
  возвращают тот же результат, а не создают второй ход.
- Исход, баланс, транзакция и запись в историю — одной операцией БД.
- Баланс изменился между открытием экрана и подтверждением — ход не выполняется,
  пользователь подтверждает заново.
- События пишутся с `source = 'roulette'`, иначе выигрыши попадут в рейтинги и
  соревнования отделов и команд.
- Выигрыш исключить из метрики «Начислено» в админской экономике; рулетку показать там
  отдельным блоком: ставки, выплаты, разница, игроки, доля обнулений. Плюс выключатель.

**Интерфейс**

- Отдельная вкладка магазина `/store?tab=roulette`.
- До хода видно ставку (весь баланс), все семь секторов с шансами и явное
  предупреждение, что почти в 30% случаев баланс обнулится.
- Подтверждение обязательно; отмена ничего не делает.
- После хода — результат, новый баланс и сообщение «ход использован, следующий с 1-го числа».
- Анимация на Framer Motion, при `prefers-reduced-motion` — сразу результат.

**Готово, когда**

- [ ] Второй ход в том же месяце невозможен ни из интерфейса, ни повторным запросом.
- [ ] Все семь исходов проверены вживую, баланс совпадает с БД.
- [ ] Блок в админской экономике сходится с транзакциями, выключатель гасит вкладку.
- [ ] «Начислено» и рейтинги от выигрышей не изменились.

## Задача 2. Приёмка ветки v2.0

Пройти вживую всё новое, собрать список проблем, **согласовать со мной**, и только после
согласования исправлять.

Что новое: корректировки задним числом, обжалование списания 💎, новости, фото и видео
в карточках товаров, подтверждение покупки, поиск в топах, прокрутка календаря,
мультиселект в админке товаров, уникальные награды достижений по месяцам,
автоприменение второй жизни, ИИ-нормоконтроль и тендерные ИИ-проекты в достижениях,
гардероб и галерея Бимо, уведомления о заказах и обращениях.

По каждому пункту три среза:

1. **Работает** — позитивный и негативный сценарий, пустые данные, двойной клик,
   две вкладки, обрыв сети.
2. **Выглядит** — 360 / 768 / 1280 / 1920 и широкие экраны, мобильное меню, свёрнутый
   сайдбар, скелетоны загрузки, страницы ошибок.
3. **Удобно** — где лишние клики, непонятные тексты и статусы, нет отклика после
   действия, нет подтверждения у необратимой операции. При такое проверке надо деражать в голове, 
   что все пользователи тупые и если им будет что-то непонятно, начнется спам в обратную связь, может где-то не хватает тултипов с пояснениями.

**Формат:** список в `src/docs-features/audit-issues.md` — описание, шаги, приоритет
(блокер / важно / мелочь), скриншот для визуальных. Сначала весь список, потом
согласование, потом правки. Всё, что меняет правила начислений или поведение данных, — только после
отдельного согласования.

**Готово, когда**

- [ ] Список собран и согласован, согласованные правки внесены.
- [ ] `tsc`, `lint` и `build` проходят, документация затронутых модулей обновлена.
