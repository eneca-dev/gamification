# Проверка безопасности магазина и галереи Бимо

Проверка 18.11.2026 по запросу пользователя. Модель угроз: вошедший сотрудник
с консолью браузера. Проверялись не намерения кода, а фактические права в базе:
что вернёт прямой запрос публичным ключом в обход интерфейса.

## Результат по Бимо

Закрыто. Таблицы `bimo_catalog`, `bimo_equipment`, `bimo_likes` имеют включённый
RLS, ноль политик и ноль грантов ролям `anon` и `authenticated` — прямой запрос
отклоняется. Функции `purchase_bimo_item`, `equip_bimo_item`, `fn_bimo_like`,
`fn_bimo_unlike`, `fn_bimo_gallery`, `fn_bimo_finalize_month` доступны только
`service_role`. Это решающее место: все они принимают идентификатор пользователя
параметром, и при публичном праве на выполнение любой сотрудник покупал бы вещи
за чужие кристаллы и голосовал от чужого имени. Публичны только `fn_bimo_month()`
и `fn_bimo_like_limit()` — строка месяца и число 3.

Серверные действия берут личность из сессии, клиент передаёт лишь идентификаторы
и ожидаемую цену, всё валидируется Zod. Цена пересчитывается на сервере по живому
курсу, списывает сумму сама база. Экипировка требует оплаченного невозвращённого
заказа на этот товар. Повторная покупка исключена блокировкой строки товара.
Бакет `bimo-assets` открыт на чтение (это картинки), политик записи для него нет —
заливает только админский маршрут сервисным ключом. `checkIsAdmin` проверяет
подпись JWT на сервере Supabase до чтения признака администратора.

## Найдено и исправлено

Вью `view_bimo_contest_winners` была `SECURITY DEFINER` с грантом для `anon`
и содержала колонку `user_email`. Публичный ключ лежит в исходном коде страницы,
поэтому список победителей с рабочими почтами читался вообще без входа.
Переведена в `security_invoker`, права публичных ролей отозваны. Галерея читает
её сервисным ключом, поведение не изменилось.

Пятнадцать функций семейства `get_adoption_*` и `adoption_*` вызывались без входа
как `SECURITY DEFINER`, среди них `adoption_designer_emails()` и
`get_adoption_red_users()`. Приложение их не использует: действующая аналитика
ходит в версии `_v2`/`_v3` сервисным ключом. Право на выполнение отозвано у ролей
`PUBLIC`, `anon` и `authenticated` по всему семейству, выдано `service_role`.
Отзыва у ролей было недостаточно: право было выдано ещё и `PUBLIC`.

Таблица `ach_ranking_snapshots_bak_20261027` лежала в схеме `public` без RLS
и читалась кем угодно. RLS включён, политик нет — доступ остался только
у сервисного ключа.

## Найдено, не исправлено

Политика `authenticated_select` на `ws_users` разрешает любому вошедшему
сотруднику прочитать справочник целиком: почты, отделы, команды и колонку
`is_admin`, то есть готовый список администраторов.

Политика `Authenticated users can read shop_products` открывает каталог целиком:
`cost_byn`, коэффициенты, скрытые позиции и невыпущенные черновики Бимо.

Проверено, что обе политики приложению не нужны: `ws_users` пользовательским
клиентом не читает ни один файл, `shop_products` читала только справка, и эти
два запроса переведены на сервисный ключ. Миграция с удалением политик
подготовлена и пользователем отклонена, решение за ним.

Остаются известными и не входили в задачу: шесть материализованных вью рейтингов
доступны `anon`/`authenticated`, вью `view_top_pers_revit_launches` объявлена
`SECURITY DEFINER`, у `fn_bimo_like_limit` и трёх функций модуля корректировок
не зафиксирован `search_path`, расширение `vector` установлено в `public`,
в Supabase Auth выключена проверка утёкших паролей.

## Проверки

После миграции повторно прогнан штатный аудит Supabase: категория
«RLS отключён в public» исчезла, из списка `SECURITY DEFINER`-функций, доступных
без входа, не осталось ни одной, из списка доступных вошедшим осталась только
`my_ws_user_id()` — она возвращает идентификатор самого вызывающего и нужна
политикам. `npx tsc --noEmit` и production-сборка прошли.
