# Модуль корректировок (admin/corrections)

## Цель

Инструмент HR/админа для исправления ошибочных данных геймификации задним числом: красный день, который должен был быть зелёным или отсутствием; пропущенный или лишний Revit-день; ошибочная транзакция. После прогона состояние пользователя должно совпадать с тем, каким оно было бы, если бы день изначально обработался правильно: стрики, бонусы за пороги, циклы, транзакции, баланс, топы.

Каждый прогон показывается пошаговым логом (терминал) — сначала как предпросмотр без изменений, затем как реальное применение.

## Текущее состояние

В репозитории есть черновик (не в проде, в рабочем дереве): `src/modules/corrections/`, страницы `src/app/(main)/admin/corrections/`, миграция `116_admin_corrections.sql` (**уже применена в боевой БД 06.10.2026**, в таблице 2 тестовые строки).

## Ключевые факты БД (сверено 09.10.2026)

**Модель стрика.** Дельты по дням: `green` = +1, нет записи в `ws_daily_statuses` (выходной/праздник) = +1, `absent` = 0, `red` = 0, но +1 при наличии записи в `streak_shield_log` на эту дату. Воспроизведено в SQL точно: у Казака Александра стрик 82 = 55 зелёных + 27 «нет записи» + 10 отсутствий. **Стрик ≠ число зелёных дней.**

**Якорь стрика восстановим.** `streak_start_date` при сбросе перезаписывается, но вычисляется обратным проходом до предыдущего красного дня без щита (или до завершения предыдущего цикла); если такого нет — начало геймификации 01.07.2026.

**Пересчёт должен быть по циклам, а не однократный.** Если восстановленный стрик пересекает порог цикла (WS 90, Revit 30) в середине окна, подход «выставить якорь и позвать `fn_catch_up_streak_milestones()`» теряет дни после пересечения. Доказано: у Рациборской Валерии исправление 2 красных дней даёт 94, пересечение 90 на 04.10, после пересечения остаётся 4 дня нового цикла (проверено: сумма дельт 05.10–08.10 = 4). Правильно: бонус на дату пересечения → `completed_cycles + 1` → новый якорь = день после → повторить с нового якоря.

**Реализация — не цикл по дням, а оконная функция.** Стрик в системе уже вычисляемый, не хранимый: после правки `ws_daily_statuses` и якоря число становится верным само, его никуда не надо писать. Дату пересечения даёт `SUM(delta) OVER (ORDER BY d)` — первый день, где накопленная сумма достигла порога. Внешний обход — по циклам, а их 0–2, то есть одна-две итерации вместо сотни.

Границы — не редкость: `ws_streak_90` сработал 38 раз с 29.09.2026; у Revit `completed_cycles` доходит до 2 за три месяца.

**Выражение дельт обязано быть одно на всю систему.** Сейчас оно продублировано дважды — в `ws_user_streaks_effective` и `revit_user_streaks_effective` (миграции 039, 072). Корректировки добавили бы третью и четвёртую копию, и расхождение в одном краевом случае (щит, перенесённый рабочий день из `calendar_workdays`, `absent` против «нет записи») дало бы «панель показывает 94, лог корректировки 93», причём подобранные тест-кейсы этого не поймают. Решение: вынести дельты в одну SQL-сущность и переиспользовать её в обоих вью и в корректировках.

Паритет кандидата с боевыми вью проверен на всех пользователях: **WS — 469 человек, 0 расхождений; Revit — 309 человек, 0 расхождений.** Эти два запроса идут в миграцию как регрессионная проверка перед переключением вью.

**Pending-сброс нужно снимать явно.** Пока `pending_reset_expires_at > now()`, вью отдаёт замороженное `current_streak` из таблицы, а `fn_catch_up_streak_milestones()` таких пользователей пропускает. Правка красного дня, по которому висит pending, не даст эффекта, пока `pending_reset_date` и `pending_reset_expires_at` не сняты. Сейчас под активным pending 37 человек по WS и 33 по Revit.

**Из `ws_user_streaks` / `revit_user_streaks` писать только `streak_start_date` и `completed_cycles`** (плюс снятие pending). `current_streak` — снапшот для ночного VPS, выставлять его руками не нужно и вредно: разъедется с вью до следующего прогона.

**Ставки читать только из `gamification_event_types`** (`src/docs/gamification-db.md` устарел в разы): `green_day` = 15, `ws_streak_7` = 100, `ws_streak_30` = 300, `ws_streak_90` = 600, `revit_streak_7_bonus` = 25, `revit_streak_30_bonus` = 100, `revit_using_plugins` = 10. С запуска не менялись — компенсировать задним числом можно по текущим.

**`ranking_date`** (миграция 112) — колонка, по которой топ-матвью считают месяц; `event_date` у `source='ws'` остаётся сдвинутым +1 триггером `fn_fix_ws_event_date`. Компенсирующим транзакциям важна верная `ranking_date`, иначе 💎 попадут в чужой месяц топа.

**Существующие функции — переиспользовать, не дублировать:**
- `fn_refresh_ranking_views()` — только `REFRESH MATERIALIZED VIEW CONCURRENTLY` по 6 топ-матвью. Именно это вызывать после корректировки. `fn_ach_snapshot_rankings()` вызывать нельзя: она ещё пишет снапшоты рейтингов и выдаёт достижения.
- `process_gamification_event(p_user_id, p_user_email, p_event_type, p_source, p_event_date, p_details, p_idempotency_key, p_coins, p_create_transaction)` — 9 аргументов.
- `trg_award_revit_points` на `elk_plugin_launches` при вставке задним числом сам создаёт событие, транзакцию и баланс, со всеми guard'ами (рабочий день, отсутствие, `is_active`), идемпотентно по `revit_green_{email}_{date}`. Стрик не трогает.

**Удаление строк возможно:** триггеров на DELETE нет. Ограничения:
- `gamification_transactions.event_id → gamification_event_logs(id)` без `ON DELETE` → порядок строгий: сначала транзакция, потом событие;
- `shop_orders.transaction_id` и `refund_transaction_id → gamification_transactions(id)` → транзакцию покупки удалить нельзя, нужен guard с понятной ошибкой вместо падения по FK;
- события `streak_reset_*` и `revit_streak_reset` транзакций не имеют вовсе (удаление = одна строка, баланс не трогается);
- `red_day` имеет транзакцию на 0💎 у 17 629 из 17 644 → удалять пару, баланс не меняется.

**Баланс нельзя пересчитывать как сумму транзакций.** Инвариант уже нарушен у 14 человек: у 12 расхождение ровно +1500💎, у одного +5000, у одного +100 — похоже на ручные начисления прямо в `gamification_balances` без транзакций. Рецепт «`UPDATE balances SET total_coins = SUM(transactions)`» из `gamification-db.md` отобрал бы у них эти 💎. Правило модуля: баланс меняется **только дельтой** удалённого или добавленного, с ограничением снизу нулём (`GREATEST(0, ...)`); существующее расхождение показывается в логе предупреждением и не правится.

**Снапшоты рейтингов за прошлые дни не исправляются.** `ach_ranking_snapshots` (12 259 строк) пишется по дням. Если корректировка задним числом поднимает человека в топ-10, дни «до» не доначислятся. Порог личного достижения — 20 дней в топ-10 за календарный месяц. Это ограничение модуля, показывать в предпросмотре.

**Стрикам из `*_user_streaks_effective` нельзя доверять как истине.** У уволенных (`is_active = false`) записи в `ws_daily_statuses` прекращаются, а «нет записи = +1» надувает счётчик на +1 в день: Денисков 93 при снапшоте 44, Станкевич 91 при 42, бонусов ноль. Пересчёт вести по фактическим статусам.

**Готовые рассинхроны:** 8 красных дней сосуществуют с отсутствием на ту же дату — первые кандидаты на исправление.

**Revit-начисление в день отсутствия — 166 исторических случаев** (июль 59, август 51, сентябрь 56; 32 человека, 1660💎), в октябре ни одного. Причина: триггер проверяет отсутствие на момент вставки, а синк отсутствий приходил позже; миграция 111 (30.09.2026) восстановила guard. То есть правило сейчас соблюдается, а 166 случаев — легаси. Отзыв Revit-начисления за день, ставший отсутствием, согласуется с текущим поведением системы; массовую чистку легаси модуль не делает (вне объёма).

## Сценарии (три, согласовано)

1. **`fix_ws_day`** — красный день → зелёный или → отсутствие. Реплей WS-стрика; при переводе в отсутствие также реплей Revit-стрика и отзыв Revit-начисления за этот день (правило миграции 111: за день отсутствия Revit-кристаллы не начисляются).
2. **`fix_revit_day`** — добавить пропущенный или убрать лишний Revit-день. Добавление — вставка в `elk_plugin_launches` (начисление делает триггер); удаление — снятие события и транзакции. Реплей Revit-стрика с циклом 30.
3. **`delete_transaction`** — удалить ошибочную транзакцию вместе с её событием, баланс дельтой.

Ручная корректировка баланса **исключена сознательно**: всё правится через источники и реплей. Новые типы событий не вводятся — работаем только существующими типами либо удаляем строки.

## Этапы реализации

### Этап 1: Миграция 117 (116 не трогаем, она в проде)

Структура — один примитив удаления, один параметризованный пересчёт, три тонкие обёртки. Две почти одинаковые функции «на 90» и «на 30» не пишем.

**1.1. Общее выражение дельт** — `fn_streak_day_delta(...)` либо вью-источник, покрывающее оба домена. Переключить на него `ws_user_streaks_effective` и `revit_user_streaks_effective`. В миграции — проверка паритета по всем пользователям до и после переключения (запросы уже написаны и дали 0 расхождений).

**1.2. Примитив `fn_correction_remove_event(p_event_id)`** — снять событие вместе с транзакцией: порядок транзакция → событие (FK без `ON DELETE`), guard по `shop_orders` (защищены только `shop_purchase`, 1132 строки — корректировка их не касается, проверка нужна от падения по FK), правка баланса дельтой `GREATEST(0, balance - coins)`. Используется всеми тремя сценариями.

**1.3. Параметризованный пересчёт `fn_correction_replay_streak(p_user, p_domain, p_from)`** — параметры: длина цикла (90/30), пороги (7/30/90 или 7/30), ключи типов событий, `source`. Внутри: восстановление якоря обратным проходом → `SUM(delta) OVER (ORDER BY d)` → дата пересечения порога → бонус → `completed_cycles + 1` → новый якорь = дата + 1 → повтор. Снятие pending, если правится именно тот день, что его вызвал. Писать только `streak_start_date` и `completed_cycles`.

Начисление бонуса — **в точности как в `fn_catch_up_streak_milestones()`**: ставка из `gamification_event_types`, `details` с `completed_cycles`, формат ключа `ws_streak_90_{user_id}_{date}`, выдача через `process_gamification_event`. Иначе появится второе определение «как выглядит бонус за 90», и ночной догон не распознает бонус корректировки как уже выданный.

**1.4. Три обёртки-сценария** — `fn_correction_fix_ws_day`, `fn_correction_fix_revit_day`, `fn_correction_delete_transaction`. Каждая: валидация → проверка противоречий → снимок «до» → примитивы → пересчёт → лог.

**1.5. Dry-run** — внутренний `BEGIN ... EXCEPTION WHEN OTHERS THEN` в той же функции: внутренний блок это подтранзакция, её откатывает, лог остаётся в переменной и возвращается обычным `RETURN`. Не «бросить исключение наружу и выковыривать лог из текста ошибки» — наружное `RAISE` уничтожит и лог.

**1.6. Рефреш топов — вне тела функции.** `fn_refresh_ranking_views()` вызывать из `applyCorrection` после коммита RPC. Причины: в dry-run он не нужен; при пакете дней рефреш должен быть один в конце, а не шесть матвью на каждый день; и если функцию когда-нибудь вызовут внутри явного транзакционного блока, `CONCURRENTLY` там недопустим. (Внутри plpgsql-функции, вызванной как отдельный оператор, `CONCURRENTLY` работает — `fn_ach_snapshot_rankings` делает это каждую ночь.)

**1.7. Журнал — только при применении.** Строку в `admin_corrections` писать из `applyCorrection`, не из функции: в dry-run запись всё равно откатится, а журналировать каждый щелчок предпросмотра — мусор. Снять политику UPDATE для `authenticated`; сократить CHECK `correction_type` до трёх сценариев.

**Края `trg_award_revit_points`, которые обязан показать лог:**
- при выходном, отсутствии или `is_active = false` триггер **молча** ничего не делает — лог должен сказать «не начислено, потому что X», а не «готово»;
- повторная вставка по тому же (email, дата) события не создаёт (`ON CONFLICT DO NOTHING`), но **дописывает элемент в `details.plugins`** — повторный прогон корректировки раздувает массив, нужен guard на уровне корректировки.

Затрагиваемые файлы: `supabase/migrations/117_corrections_functions.sql`.

Зависимости: нет.
