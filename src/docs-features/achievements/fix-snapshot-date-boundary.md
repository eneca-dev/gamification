# Исправление границы даты в снапшотах достижений

## Цель

`fn_ach_snapshot_rankings` подписывает снапшот вчерашним числом (`v_today = fn_minsk_today() - 1`),
но берёт данные из матвью `view_top_*`, у которых верхняя граница — `fn_minsk_today()`, то есть
сегодня. Отложенные WS-награды за задачи (`budget_ok_l3`, `deadline_ok_l3`, `master_planner`)
получают `ranking_date` = день начисления и создаются в том же ночном прогоне за минуту до
снапшота. Поэтому «сегодняшние» монеты попадают во «вчерашний» топ.

Сделать так, чтобы топ за дату D считался строго по монетам с `ranking_date <= D`, и чтобы
расхождение между записанным и расчётным топом обнаруживалось автоматически.

## Контекст: подтверждённый случай

16.10.2026 снапшот записал топ по состоянию на 17.10 (снапшоты за 16.10 и 17.10 совпали
строка в строку). Команды ВК-6 (+1115 💎) и ВК-4 (+1432 💎) вытеснили из топ-5 «Команду
ОВ гражд-1» и «Разработка - JS/TS». Данные восстановлены миграцией
`139_restore_lost_ws_snapshot_2026_10_16.sql` (только добор строк, удалений нет).

Завышенный `score` детектируется в 13 днях октября из 26; состав топа поменялся только 16.10,
потому что в ту ночь пришёл самый большой пакет задачных наград за месяц.

Revit-ветка чистая: revit-события датируются вчерашним днём, сравнение по всем 26 дням октября
расхождений не дало.

## Этапы реализации

### Этап 1: расчёт топа на заданную дату (критичный) — СДЕЛАНО

Миграции `140_rank_functions_by_date.sql` и `141_snapshot_uses_rank_functions.sql`.
Замена `row_number()` на `dense_rank()` из этапа 1 вынесена в этап 3: это
изменение поведения, а не исправление даты, и в одной миграции с ним снапшот
начал бы расходиться с вкладкой «Топы».

Проверено после применения: `fn_rank_pers_ws(сегодня)` и
`fn_rank_pers_revit(сегодня)` совпадают с матвью построчно; формула
`fn_rank_dept_ws` воспроизводит `view_top_dept_ws` при дословно том же окне;
`fn_rank_team_ws('2026-10-16')` ставит «Команду ОВ гражд-1» на 5 место, ВК-6 и
ВК-4 — вне топ-5.


- Создать 6 SQL-функций, повторяющих формулы текущих матвью, но с параметром даты:
  - `fn_rank_pers_ws(p_date date)`, `fn_rank_team_ws(p_date)`, `fn_rank_dept_ws(p_date)`
  - `fn_rank_pers_revit(p_date)`, `fn_rank_team_revit(p_date)`, `fn_rank_dept_revit(p_date)`
- Границы внутри функций: `ranking_date` (ws) / `event_date` (revit) `BETWEEN date_trunc('month', p_date) AND p_date`,
  отсутствия — на `p_date`.
- В `fn_ach_snapshot_rankings` заменить чтение матвью на вызов функций с `p_date := v_today`.
- Матвью на этом этапе **не трогать** — они обслуживают живой топ на «сегодня» и это корректно.

Затрагиваемые файлы: новая миграция `supabase/migrations/140_*.sql`.
Зависимости: нет.

Побочный эффект: формула временно существует в двух местах (функция + матвью). Снимается этапом 4.

### Этап 2: аудит снапшотов

- `ALTER TABLE ach_ranking_snapshots ADD COLUMN created_at timestamptz NOT NULL DEFAULT now()`.
- Функция `fn_ach_audit_snapshot(p_date date)` — сравнивает записанный состав топа за `p_date`
  с расчётом функций из этапа 1, возвращает расхождения (`missing` / `extra` / `score_mismatch`).
- В `src/scripts/compute-achievements.ts` (репозиторий `gamification-vps-scripts`) вызвать аудит
  после снапшота и положить результат в `stats` — оркестратор уже умеет выводить массивы
  `*_errors` / `warning*` в телеграм-отчёт.

Затрагиваемые файлы: миграция; `gamification-vps-scripts/src/scripts/compute-achievements.ts`;
`gamification-vps-scripts/docs/scripts/compute-achievements.md`.
Зависимости: этап 1.

### Этап 3: детерминированные ничьи — СДЕЛАНО

Миграция `143_group_rankings_dense_rank.sql` (функции) и `144_*.sql` (один
доначисленный день). Приоритет оказался выше запланированного: расхождение уже
работало. Фронтенд считает места через `dense_rank` (`DepartmentContest.tsx`,
`applyDenseRank`), база считала через `row_number` — команда, пятая на экране,
в снапшоте оказывалась шестой. Так «Команда ОВ гражд-1» потеряла 25, 26 и 27
октября при ничьих 955.0 / 970.0 / 985.0 у двух команд выше.

Матвью `view_top_team_*` и `view_top_dept_*` остались на `row_number`: на
дашборде места пересчитываются на клиенте, их `rank` влияет только на бейдж
«#N» в блоке достижений.

Доначислено только 27.10 по обращению команды; 25 и 26 октября и дни других
команд, потерянные так же, оставлены без изменений — решение не доначислять
задним числом.


- В командных и отдельских рейтингах заменить `row_number()` на `dense_rank()` — как в личных.
- Правится в функциях этапа 1 и в матвью (если этап 4 ещё не сделан — в обоих местах).

Сейчас при равном счёте позиция определяется произвольно и может меняться между пересчётами.
Ничьи на 4–5 месте за сентябрь–октябрь встречались 5 раз; на границе 5/6 это означало бы
случайную потерю дня.

Затрагиваемые файлы: миграция.
Зависимости: этап 1.

### Этап 4: матвью через те же функции (устранение дублирования)

- Переопределить `view_top_pers_ws`, `view_top_team_ws`, `view_top_dept_ws`,
  `view_top_pers_revit`, `view_top_team_revit`, `view_top_dept_revit` как
  `SELECT * FROM fn_rank_*(fn_minsk_today())`.
- Сохранить имена колонок (`rank`, `team` / `department_code` / `user_id`, `users_earning`,
  `total_employees`, `total_coins`, `contest_score`, `period_start`) — их читает фронт.
- Пересоздать unique-индексы (нужны для `REFRESH ... CONCURRENTLY`) и выполнить `REFRESH`.
- Попутно выровнять окно отсутствий: сейчас `view_top_team_ws` и `view_top_pers_ws` берут
  `absence_date = fn_minsk_today()`, а `view_top_dept_ws` и revit-вью — `fn_minsk_today() - 1`.

Прецедент DROP + CREATE всех трёх WS-матвью есть в `112_add_ws_ranking_date.sql`.

Затрагиваемые файлы: миграция.
Зависимости: этапы 1, 3.

### Этап 5: месяц в благодарностях по минскому времени

- `fn_ach_check_gratitude_achievements` и `fn_ach_get_gratitude_progress`: границу месяца строить
  от `fn_minsk_today()`, а не от `CURRENT_DATE`, и сравнивать `created_at` с минским временем,
  а не с датой в UTC (таймзона БД — UTC, из-за чего месяц сдвинут на 3 часа).
- `getGratitudeProgressAll` в `src/modules/achievements/queries.ts` считает начало месяца через
  `new Date()` — серверное локальное время; привести к той же логике.

Потерь пока нет: в окно 00:00–03:00 по Минску первого числа за сентябрь и октябрь не попал ни
один подарок. Дефект латентный.

Затрагиваемые файлы: миграция; `src/modules/achievements/queries.ts`.
Зависимости: нет.

## Критерии готовности

- [ ] `fn_ach_snapshot_rankings` не читает матвью; снапшот за дату D считается по монетам с датой `<= D`
- [ ] Прогон функции на тестовой дате воспроизводит корректный топ-5 за 16.10 (ОВ гражд-1 на 4 месте)
- [ ] `ach_ranking_snapshots.created_at` заполняется
- [ ] `fn_ach_audit_snapshot` на 16.10 показывает расхождения, на 24.10 — нет
- [ ] Расхождения попадают в телеграм-отчёт блока Achievements
- [ ] Ничьи в командных и отдельских топах разрешаются через `dense_rank`
- [ ] Формула рейтинга существует в одном месте
- [ ] Благодарности считают месяц по Минску
- [ ] `npm run build` и `npm run lint` проходят
- [ ] Ни одна строка в `ach_ranking_snapshots` и `ach_awards` не удалена; балансы не изменились

## Ограничения

- Снапшоты за прошлые месяцы не пересчитываются: `ws_users` не хранит историю состава команд
  (`team` перезаписывается синком), поэтому исторический делитель невосстановим.
- Уже выданные награды не отзываются — принцип из `114_fix_revit_contest_formula_and_award_september.sql`
  («previously granted awards are intentionally kept»).
- Фантомные строки за 16.10 (ВК-6, ВК-4, ВК) оставлены намеренно: удаление опустило бы их
  счётчики на экране и обнулило бы основание под уже выданными наградами.
