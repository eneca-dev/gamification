## Порядок и зависимости

1. Проверить официальный архив/контрольную сумму Go, собрать закреплённый Auth. При ошибке Windows-сборки показать конкретный лог; Docker/WSL не устанавливать автоматически. WSL-проверка ранее вернула E_ACCESSDENIED, что не доказывает отсутствие WSL.
2. Создать отдельный кластер: роли общие для всего PG-кластера, а проверенный roulette_qa_exact запрещает memberships. Существующие 5432 и 55437 не менять. Применять только Auth schema migrations выбранной версии и проверенный декларативный public baseline, SQL01/02 и согласованную коррекцию ACL. Исторические миграции приложения не проигрывать. В preflight добавить DEFAULT PRIVILEGES и фактические права новых объектов.
3. Дополнить baseline необходимой day_off_requests и собственным чтением profiles через RLS; подготовить roles/authenticator для PostgREST. Без cron/net/SMTP/webhooks/OAuth providers. Только synthetic users, ws_users, profiles, balances и курс. Не копировать auth.users(id)-заглушку вместо настоящей Auth schema.
4. Из отдельного каталога исходников без .env.local собрать Next16 production. Только локальные URL/ключи; отдельный HMAC secret и synthetic pilot email, ENABLE_DEV_TOOLS=false, BIMO_V2_ENABLED=false. Не использовать рабочие cookie/storageState. Включение и тестовые ходы допускаются только после проверки маркеров этого изолированного контура; рабочий выключатель остаётся false.
5. Подготовить Playwright auth setup через настоящий Auth password login: проверить отказ без сессии и с неверным паролем, затем auth.getUser и привязку app_metadata.ws_user_id. Сессию создавать настоящим Supabase SSR client, не подделывать JWT. В suite добавить строго проверяемый локальный backend URL вместо hosted-only URL, существующий запрет рабочего проекта сохранить.
6. Пользователь A: UI подтверждение → настоящий Server Action → PostgREST RPC → event + delta-проводка + баланс. Проверить БД отдельным соединением, UI после invalidation и reload. Предварительно прогреть серверный баланс, чтобы тест не свёлся к холодному чтению.
7. Пользователь B: route.fetch для действия → независимое подтверждение COMMIT в БД → abort ответа → неопределённый UI → reload → recovery. Сверить operationId/period, ровно одну проводку/событие и актуальный баланс. После исходного хода выполнить локальное synthetic начисление, чтобы исторический balance_after отличался от текущего. Проверить повтор того же запроса без второго списания.
8. Записать SQL-снимки, количество строк, UI-assertions, сетевой журнал и trace; завершить процессы, выключить локальную рулетку. Публикация не нужна.

## Что этим не подтверждается

- Вход кнопкой Worksection: endpoints заданы в src/config/worksection.ts. Нужны отдельно согласованные тестовый OAuth-клиент, аккаунт и callback. Локальный Auth покрывает авторизацию и дальнейший финансовый путь, но не внешний OAuth.
- Realtime: QueryProvider всегда подключает RealtimeSync. Без настоящего Realtime нельзя считать проверенной его доставку между вкладками. Для указанной цепочки проверяются action/invalidation/refetch; отсутствующий realtime endpoint не подменять успешной заглушкой.
- Airtable/Teams/Storage, остальные функции v2.0 и замеры производительности — отдельные этапы.

## Критерий готовности

Зелёный результат только после исполнения обоих настоящих финансовых сценариев на Next production с Auth/PostgREST/PG, доказанной изоляцией и независимой проверкой БД. На текущем шаге подтверждён первый блокер: нет Go/Auth/PostgREST. Для запуска внешнего Worksection OAuth дополнительно нужны тестовые реквизиты.
