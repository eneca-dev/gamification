# Стандартный локальный Supabase: диагностика

18.11.2026. Проверены доступность команд, CLI help/status и Docker/WSL. Контейнеры не создавались, supabase start/db reset не запускались, исторические миграции не проигрывались. Сборка Auth из исходников не начиналась.

## Факты

- Supabase CLI2.64.2 найден в npm-cache/_npx/aa8e5c70f9d8d161/node_modules/supabase/bin/supabase.exe. В PATH и node_modules проекта его нет, но бинарник исполняется. Проверены --version, --help, start --help, status --help.
- Стандартный start запускает контейнеры gotrue, postgrest, gateway и прочих сервисов. Установленного PostgreSQL отдельно недостаточно для этого режима.
- Docker CLI28.4.0 установлен; context desktop-linux. version/info возвращают HTTP500 от dockerDesktopLinuxEngine по API1.51. Серверная часть не подтверждена работоспособной.
- supabase status завершается кодом1: доступ к named pipe docker_engine запрещён. Docker config.json и каталог contexts также недоступны текущей сессии.
- docker desktop status не может писать собственный диагностический лог и прочитать конфигурацию (Access denied), поэтому не установлено, работает ли Desktop в пользовательской сессии.
- WslService запущена; wsl --status и --list --quiet возвращают Wsl/E_ACCESSDENIED. Это не доказательство отсутствия WSL.
- com.docker.service остановлена/manual; сама по себе эта строка не доказывает неисправность WSL backend.

## Вывод и ближайший шаг

Стандартный вариант сейчас заблокирован из этой агентской сессии доступом к Docker/WSL и ответом500 Linux Engine. Не требуется сразу переходить к portable или устанавливать Docker заново.

Нужно проверить Docker Desktop и docker info в обычном пользовательском терминале. Если раздел Server доступен там, требуется предоставить рабочий доступ к Docker текущей сессии. Если и там ошибка, сначала восстановить работу Desktop/WSL. Настройки безопасности, elevation и системные службы автоматически не менялись.

После доступности Engine: отдельный CLI workdir с собственной config.toml и пустой историей migrations; только одобренный безопасный baseline/синтетические данные. Запуск из корня с имеющимися историческими migrations запрещён. Рабочие URL/ключи и OAuth/HTTP/cron назначения не переносятся. Затем настоящий Next production runtime и цепочка приёмки из full-e2e-preparation.md.

## Portable — оценка, не начатая работа

Ориентир: 2–4 рабочих дня на изолированный PG + Auth + PostgREST + gateway, подготовку production runtime и сквозной сценарий. Из них 0.5–1 день — проверка native Auth/Windows. Оценка предполагает успешную сборку; при несовместимости потребуется пересмотр. Время ожидания доступов не включено. Новые платные/облачные ресурсы не предлагаются.

Рекомендация: сначала восстановить стандартный Docker/CLI путь. Portable сложнее воспроизвести и обслуживать, а Windows Auth пока не проверен. Сборку из исходников не начинать без нового указания пользователя.
