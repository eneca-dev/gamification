# ТЗ: рулетка 💎, приёмка и доработка Бимо

Исполнитель — разработчик проекта (Next.js 15 / React 19 / Supabase). Перед началом прочитать
`CLAUDE.md`, `src/docs/dev-pipeline.md`, `src/modules/cache/README.md`, `src/docs/shop.md`,
`src/docs/admin.md`, `src/docs/profile-appearance.md`.

Масштаб — **Full Pipeline**: новый модуль, новая миграция БД, правки в магазине и админке.
Ветка: `feature/roulette`. Один этап = один коммит в формате `тип(модуль): описание`.

Работа разбита на 7 этапов. Этапы 1–4 — рулетка, 5–6 — приёмка и баги, 7 — Бимо.
Этапы 1→4 строго последовательны; 5–7 можно выполнять после 4 в любом порядке.

## 0. Согласованные правила игры

Решения заказчика (отменяют вопросы в `plan.md`):

| Параметр | Значение |
| --- | --- |
| Ставка | Весь баланс сотрудника на момент подтверждения |
| Исходы | 50/50: баланс становится `0` либо `2 × ставка` |
| Допуск | Любой баланс > 0 |
| Частота | **Без ограничений** — сколько угодно ходов |
| Потолок выигрыша | Нет |
| Управление | Статистика и выключатель в админке → «Экономика» |
| Размещение | Отдельная вкладка магазина: `/store?tab=roulette` |

Экономические расчёты и риски — `src/docs-features/roulette/plan.md`. **Важно:** таблицы риска
из `plan.md` посчитаны для одного хода на человека и при неограниченной частоте недействительны.
Математическое ожидание остаётся нулевым, но разброс не ограничен: 10 побед подряд дают
`1024 ×` исходный баланс с вероятностью `1/1024` на серию, а при 464 играющих такие серии
за месяц ожидаемы. Поэтому обязательны: выключатель (этап 4), видимая в админке эмиссия
за период (этап 4) и исключение рулетки из рейтингов и метрики «Начислено» (этапы 1 и 4).
Перед открытием доступа всем — согласовать запас призов магазина и правила с HR.

## Этап 1. База данных и атомарный ход

**Файл:** `supabase/migrations/147_roulette.sql` (последняя занятая — 146).
Применять через MCP `apply_migration` или Supabase CLI.

### 1.1 Типы событий

Добавить в `gamification_event_types` две строки (образец — `shop_purchase`):

| key | name | coins | is_dynamic_coins | create_transaction | is_active |
| --- | --- | --- | --- | --- | --- |
| `roulette_bet` | Ставка в рулетке | 0 | true | false | true |
| `roulette_win` | Выигрыш в рулетке | 0 | true | false | true |

Суммы динамические — их пишет функция хода, не справочник.
`is_active` у `roulette_bet` служит выключателем игры (идиома проекта: так же выключен
`streak_daily_bonus` через `fn_set_streak_daily_bonus_enabled`).

### 1.2 Функция хода `fn_roulette_spin`

```
fn_roulette_spin(p_user_id uuid, p_expected_balance integer, p_request_id uuid)
  returns jsonb
```

Возврат: `{ outcome: 'win' | 'lose', bet, balance_before, balance_after, request_id, replayed }`.

`SECURITY INVOKER`, `LANGUAGE plpgsql`, вызов только через `supabaseAdmin` (service_role) —
как `purchase_product`. Эталон по структуре и блокировкам — `purchase_product`.

Последовательность внутри одной транзакции:

1. **Идемпотентность.** Если в `gamification_event_logs` уже есть запись с
   `idempotency_key = 'roulette_bet_' || p_request_id` — вернуть сохранённый в `details`
   результат с `replayed: true` и ничего не менять. Это и есть защита от двойного клика,
   второй вкладки и повторной отправки: уникальный индекс
   `gamification_event_logs_idempotency_key_key` гарантирует её на уровне БД.
2. **Выключатель.** `roulette_bet`.`is_active = false` → `RAISE EXCEPTION 'roulette_disabled'`.
3. **Антиспам.** Если у пользователя есть событие `roulette_bet` с
   `created_at > now() - interval '3 seconds'` → `RAISE EXCEPTION 'roulette_too_fast'`.
   Частота ходов не ограничена, но защита от скриптового перебора нужна; константу
   вынести в начало функции отдельной переменной, чтобы её легко было поменять или убрать.
4. **Блокировка баланса.** `SELECT total_coins INTO v_balance FROM gamification_balances
   WHERE user_id = p_user_id FOR UPDATE`. Не найдено или `v_balance <= 0` →
   `RAISE EXCEPTION 'roulette_no_balance'`.
5. **Сверка ставки.** `v_balance <> p_expected_balance` →
   `RAISE EXCEPTION 'roulette_balance_changed'`. Пользователь видел другую сумму —
   ход не выполняется, клиент переспрашивает.
6. **Исход.** `random() < 0.5` → `'win'`. Исход считает только сервер.
7. **Проводки.** Всегда пишется ставка, при победе — ещё и выплата:
   - `roulette_bet`: `gamification_event_logs` (`source = 'roulette'`,
     `event_date = fn_minsk_today()`, `ranking_date = event_date`,
     `idempotency_key = 'roulette_bet_' || p_request_id`,
     `details` = `{bet, outcome, balance_before, balance_after}`) +
     `gamification_transactions.coins = -v_bet`.
   - `roulette_win` (только при победе): событие с
     `idempotency_key = 'roulette_win_' || p_request_id` +
     транзакция `coins = +2 * v_bet`.
   - Итог: проигрыш `−bet`, победа `+bet`. Разделение на ставку и выплату нужно админке:
     «сумма ставок», «сумма выплат», `Δ = выплаты − ставки`.
   - `byn_amount` заполняет триггер `trg_set_byn_amount` — вручную не писать.
8. **Баланс.** `UPDATE gamification_balances SET total_coins = <0 или 2*bet>,
   updated_at = now()`. Отрицательным баланс стать не может.

**`source = 'roulette'` обязателен.** Рейтинговые materialized views
(`view_top_pers_ws`, `view_top_team_ws`, `view_top_dept_ws`, `view_top_pers_revit`,
`view_top_team_revit`, `view_top_dept_revit`) фильтруют по `e.source IN ('ws'|'revit')`,
поэтому с новым источником выигрыши не попадут в личные, командные и отдельские топы
и не исказят соревнования. Перед релизом проверить все шесть определений
(`pg_get_viewdef`), что фильтр по source действительно есть.

### 1.3 Выключатель

```
fn_set_roulette_enabled(p_enabled boolean) returns void
```

Переключает `is_active` у обеих строк `roulette_*`. Доступ — только service_role
(см. `145_revoke_correction_functions_public_access.sql` как образец отзыва прав у public).

### 1.4 Критерии готовности этапа

- [ ] Миграция применена, функции созданы, права у `public` отозваны.
- [ ] Два ручных вызова с одним `p_request_id` дают один ход и `replayed: true` на втором.
- [ ] Параллельные вызовы (две сессии psql) не уводят баланс в минус и не создают двух ходов.
- [ ] `p_expected_balance` с устаревшим значением возвращает `roulette_balance_changed`.
- [ ] После `fn_set_roulette_enabled(false)` ход падает с `roulette_disabled`.
- [ ] Личный, командный и отдельский топы после 10 тестовых ходов не изменились.

## Этап 2. Модуль `src/modules/roulette`

Структура по `CLAUDE.md`:

```
src/modules/roulette/
  actions.ts        # 'use server': spinRoulette
  queries.ts        # 'server-only': getRouletteState, getRouletteHistory
  types.ts          # Zod-схемы + типы
  hooks.ts          # клиентские хуки через фабрики @/modules/cache
  components/       # RouletteTab, RouletteSpinner
  index.ts          # серверный API
  index.client.ts   # клиентский API (типы + actions)
```

### 2.1 Контракты

- `spinRoulette({ request_id, expected_balance })` — `request_id` генерирует клиент
  (`crypto.randomUUID()`) до вызова; Zod `safeParse` (`uuid`, `int().positive()`),
  без try/catch вокруг парсинга. Пользователь берётся из серверной сессии
  (`getCurrentUser().wsUserId`) — клиентский id не принимать.
  Возврат — `ActionResult<RouletteSpinResult>` из `@/modules/cache`.
  Текст ошибок маппить по коду из RAISE: `roulette_disabled` → «Рулетка временно недоступна»,
  `roulette_no_balance` → «Нужен положительный баланс», `roulette_balance_changed` →
  «Баланс изменился — подтвердите ставку заново», `roulette_too_fast` → «Слишком часто,
  подождите пару секунд». Неизвестную ошибку не показывать «как есть».
- После мутации: `revalidatePath('/store')` и инвалидация `queryKeys.balance.all`,
  `queryKeys.roulette.all`.
- `getRouletteState(wsUserId)` — `{ enabled, balance, history }`. `enabled` читать из
  `gamification_event_types.is_active` ключа `roulette_bet`.
- `getRouletteHistory(wsUserId, limit = 10)` — последние ходы из
  `gamification_event_logs` (`source = 'roulette'`, `event_type = 'roulette_bet'`):
  дата, ставка, исход, баланс после. Брать из `details`, не пересчитывать.

### 2.2 Кэш

- Добавить в `src/modules/cache/keys/query-keys.ts`:
  `roulette: { all: ['roulette'], user: (userId) => [...all, userId] }`.
- Хуки — только через `createCacheQuery` / `createCacheMutation`. Прямой импорт
  `@tanstack/react-query` в модуле запрещён.
- `src/modules/cache/realtime/config.ts` править не нужно: подписка на INSERT в
  `gamification_transactions` уже инвалидирует `queryKeys.balance.all` — баланс в сайдбаре
  обновится сам. Добавить в тот же `invalidateKeys` ключ `queryKeys.roulette.all`.

### 2.3 Критерии готовности этапа

- [ ] `npx tsc --noEmit` и `npm run lint` чисто, `any` нет.
- [ ] Клиентские компоненты импортируют только `@/modules/roulette/index.client`.
- [ ] Повторный вызов `spinRoulette` с тем же `request_id` возвращает тот же результат.
- [ ] Вызов без авторизации/без `wsUserId` возвращает `{ success: false }`, а не падает.

## Этап 3. Вкладка «Рулетка» в магазине

### 3.1 Интеграция вкладки

Сейчас в `src/app/(main)/store/page.tsx` и `src/modules/shop/components/StoreClient.tsx`
особая вкладка одна — Бимо, через булев `bimoActive` и ветку в `selectFilter`.
**Не плодить второй булев флаг.** Заменить на одно поле:

```ts
type StoreSpecialTab = 'bimo' | 'roulette'
// StoreClient: specialTab?: StoreSpecialTab | null, specialContent?: ReactNode
```

- `page.tsx`: `params.tab` → `specialTab`; данные рулетки грузить только когда
  `specialTab === 'roulette'` (как сейчас `getBimoState`). `key` у `StoreClient`
  пересобрать из `specialTab ?? selectedCategory ?? 'all'`.
- Чип «Рулетка» в ряду фильтров — рядом с «Енот-Бимо», тем же стилем
  (`var(--apex-primary)` активный / `var(--surface-elevated)` неактивный).
  Чип виден только при `enabled`.
- Прямой переход на `/store?tab=roulette` при выключенной игре — вкладка открывается
  с сообщением «Рулетка временно недоступна», кнопки нет.
- Переключение на обычную категорию с особой вкладки — через `router.push`, как сейчас.

### 3.2 Компонент игры

Серверный `RouletteTab` отдаёт данные, клиентский `RouletteSpinner` (`'use client'`)
отвечает за взаимодействие. Требования:

- **Видно до хода:** текущий баланс как размер ставки, «шанс 50/50», оба исхода
  (`0 💎` и `2 × ставка`), кнопка «Поставить всё и крутить».
- **Подтверждение обязательно** — модалка/портал по образцу `PurchaseButton`
  (без прокрутки страницы, с суммой ставки и обоими исходами). Отмена ничего не вызывает.
- **Исход только с сервера.** Анимация стартует сразу после подтверждения и
  останавливается на фактическом результате ответа. Клиент не выбирает исход и не
  показывает результат до ответа.
- **Пока ход в полёте:** кнопка заблокирована (`isPending` из `useTransition`),
  повторное нажатие и второй `request_id` исключены. На каждый подтверждённый ход —
  ровно один `request_id`.
- **После хода:** новый баланс, подпись исхода, обновлённая история последних 10 ходов.
  Баланс в сайдбаре обновляется сам (инвалидация `queryKeys.balance`); дополнительно
  сделать optimistic update на самой вкладке с откатом при ошибке (правило `CLAUDE.md`).
- **Нулевой баланс:** кнопка заблокирована с объяснением, ход не отправляется.
- **Ошибки сервера** показывать текстом рядом с кнопкой, не глотать.

### 3.3 Визуал

- Только Apex UI Kit (`src/docs/apex-ui-kit.md`) и Tailwind. Цвета — только переменные
  `--apex-*`, никаких HEX/RGB и `style={{}}` с произвольными цветами.
- Суммы 💎 — через `CoinIcon` / `CoinStatic` / `CoinBalance`. Эмодзи и слово «монет» запрещены.
- Анимация — Framer Motion. При `prefers-reduced-motion: reduce` вращения нет:
  сразу итоговое состояние.
- Mobile-first: проверить 360, 768, 1280, 1920 и брейкпоинты `3xl`/`ultrawide`
  (см. `LayoutShell`). Горизонтального скролла страницы быть не должно.
- `src/app/(main)/store/loading.tsx` уже есть — убедиться, что скелетон не ломается
  при `?tab=roulette`; при необходимости добавить заглушку блока рулетки
  (`#E5E7EB`, `animate-pulse`).
- Онбординг: шаг тура для вкладки добавлять только если заказчик попросит;
  тогда — `data-onboarding` + правка `storeTour` в `src/modules/onboarding/tours/store.ts`.

### 3.4 Критерии готовности этапа

- [ ] Вкладка открывается с главной и по прямой ссылке, назад/вперёд браузера работают.
- [ ] Двойной клик, два таба, обновление страницы в середине хода не создают второй ход.
- [ ] Выигрыш и проигрыш отрисованы, баланс в сайдбаре и на вкладке совпадают с БД.
- [ ] Пустой баланс, выключенная игра и ошибка сети дают понятные сообщения.
- [ ] `npm run build` проходит.

## Этап 4. Админка → «Экономика»

### 4.1 Исключить рулетку из метрик заработка

Критично и делается в том же этапе, что и статистика.

- `get_economy_overview`: CTE `earned` считает `SUM(t.coins) WHERE t.coins > 0` **без фильтра
  по источнику**, поэтому выигрыш попадёт в «Начислено» и в `factually_earned`.
  Исключить транзакции с `source = 'roulette'` из `earned` (и из `revoked`, если туда
  попадает ставка) и показывать рулетку отдельным каналом.
- `get_economy_top`: источник `'earned'` проверить на ту же проблему; добавить источник
  `'roulette'` (значение — Δ или сумма ставок, решить при реализации и описать в доке).
- Проверить и при необходимости поправить остальные места, где суммируются `coins` без
  фильтра по source: `get_economy_category_breakdown`, `get_user_period_balance`,
  `get_adoption_period_core_v2`, `get_adoption_period_engagement_v2`,
  `get_adoption_monthly_summary_v3`, `get_adoption_monthly_rankings_v2`.
  Для каждой записать в PR вывод «затронута / не затронута».

### 4.2 Канал «Рулетка» в обзоре

- SQL: добавить CTE `roulette` и ключ `'roulette'` в `jsonb_build_object('channels', …)`
  функции `get_economy_overview`. Поля: `bets` (сумма ставок), `payouts` (сумма выплат),
  `delta` (`payouts − bets`), `players` (уникальные игроки), `spins` (число ходов),
  `win_rate` (доля побед).
- TypeScript: расширить `EconomyChannels` и `TopSource` в `src/modules/admin/types.ts`.
  Каналы — нетипизированный `jsonb` на выходе RPC, поэтому поля описать явно.
- UI: блок «Рулетка» в `src/modules/admin/components/economy/EconomyDashboard.tsx`
  (рядом с `SpendingBreakdown`). Рулетка — не расход, а ±эмиссия, поэтому отдельным блоком,
  а не карточкой внутри «расходов». Показать: ставки, выплаты, `Δ` со знаком, игроки,
  ходы, доля побед; суммы — в 💎 и в BYN через `coinsToByn` + `formatByn` по текущему курсу.
- Блок подчиняется выбранному периоду дашборда (`resolveEconomyPeriod`), как остальные.

### 4.3 Выключатель

- Server Action в `src/modules/admin/actions.ts` → `fn_set_roulette_enabled`,
  только админ (`checkIsAdmin`), по образцу `fn_set_streak_daily_bonus_enabled`.
- Переключатель в блоке «Рулетка», с подтверждением и текущим состоянием.
  После переключения — `revalidatePath('/admin/economy')` и `revalidatePath('/store')`.
- Выключение не отменяет прошлые ходы и не возвращает ставки.

### 4.4 Критерии готовности этапа

- [ ] До первого хода блок показывает нули, не падает и не ломает период.
- [ ] После тестовых ходов цифры сходятся с суммами из `gamification_transactions`.
- [ ] «Начислено» и «Фактически заработано» не изменились от выигрышей.

- [ ] Неадмин на `/admin/economy` получает редирект.

## Этап 5. Полное ручное тестирование и визуальные правки

Проходится вживую, с записью результата по каждому пункту (✅ / ❌ + что именно).
Найденные дефекты исправляются здесь же, кроме требующих решения заказчика —
их выписать отдельным списком.

### 5.1 Рулетка: позитив

- [ ] Выигрыш: баланс `2 ×`, транзакции `−bet` и `+2 bet`, история и сайдбар сходятся.
- [ ] Проигрыш: баланс `0`, транзакция `−bet`, вкладка предлагает вернуться, когда 💎 появятся.
- [ ] Серия из 5 ходов подряд: баланс и история корректны на каждом шаге.
- [ ] Ход с баланса 1 💎 и с крупного баланса (> 10 000 💎).
- [ ] Страница «Мои транзакции» и лента показывают ходы с понятными названиями.

### 5.2 Рулетка: негатив и edge-cases

- [ ] Баланс 0 — кнопки нет, прямой вызов action возвращает ошибку.
- [ ] Баланс изменился между открытием вкладки и подтверждением (начислить 💎 из админки
      в соседней вкладке) — просьба подтвердить заново, ход не выполнен.
- [ ] Двойной клик, Enter×3, две вкладки одновременно — один ход.
- [ ] Обрыв сети в момент хода: повтор с тем же `request_id` даёт тот же исход.
- [ ] Выключенная рулетка: чип скрыт, прямая ссылка даёт сообщение.
- [ ] Антиспам 3 сек срабатывает и объясняется пользователю.
- [ ] Пользователь без `wsUserId` (нет записи в `ws_users`) не падает в 500.

### 5.3 Визуальная проверка (всё приложение, не только рулетка)

- [ ] Брейкпоинты 360 / 768 / 1280 / 1920 / `3xl` / `ultrawide`: нет наложений,
      обрезанного текста, горизонтального скролла.

## Этап 7. Доработка Бимо: дефекты движений

Бимо живёт в сайдбаре над блоком баланса; каждое нажатие проигрывает следующее движение
по кругу: кофе → презентация → прыжок с кристаллом (`src/docs/profile-appearance.md`).
Жалоба: мелкие дефекты при движении, особенно в разной одежде.

### 7.1 Что известно о причинах

- **Якорные точки глаз на костюм.** `src/modules/profile-appearance/scenes.ts`:
  `bimoEyes(outfit, action, frame)` для `coral-shirt` и `blue-bomber` берёт полные таблицы
  (`CORAL_SHIRT_EYES`, `BLUE_BOMBER_EYES`), для `lavender-sweater` — только `coffee` и
  `crystal`, а **презентация у свитера явно исключена** (`action.id !== 'present'`) и
  падает на точки классического Бимо. У `hoodie` своей таблицы нет вообще — все три
  движения используют классические координаты, хотя листы худи (`-v2`) рисуют другого
  персонажа. Это прямая причина смещения очков, наушников и кепки в этих комбинациях:
  растровый аксессуар позиционируется через поворот и масштаб по двум точкам глаз
  (`drawRasterAccessory` в `BimoPortrait.tsx`).
- **Разные размеры кадров.** Кофе — ячейка 256×256, презентация — 384×256, прыжок —
  384×320 при холсте 384×320. Поза покоя рисуется из портрета как `drawImage(portrait,
  0, 64, 256, 256)`, а кадры движения — от левого края с привязкой к низу
  (`HEIGHT - action.height`). Для кофе это совпадает, для презентации и прыжка силуэт
  может смещаться по горизонтали — проверить, нет ли «подскока» персонажа в первый кадр.
- **Фон не следует за прыжком** — так задумано, подтвердить, что выглядит нормально.
- Кадры меняются целиком, без смешивания; при `prefers-reduced-motion` движение не
  запускается — это ожидаемое поведение, не дефект.

### 7.2 Что сделать

1. Снять покадровые скриншоты каждой комбинации и зафиксировать дефекты списком:
   **5 костюмов** (`classic`, `hoodie`, `lavender-sweater`, `blue-bomber`, `coral-shirt`)
   × **3 движения** × **4 слота аксессуара** (`none`, `round-glasses`, `blue-headphones`,
   `mint-cap`). Для примерки без покупок использовать режим «Примерка без сохранения»
   в магазине (доступен только в development).
2. Завести собственные таблицы точек для `hoodie` и дополнить `lavender-sweater`
   движением `present`; убрать ветку-исключение из `bimoEyes`. Координаты подбирать
   покадрово по фактическим листам, в runtime — только готовые числа
   (инструмент подготовки лежит в `.local-assets/profile-appearance/tools/`, в Git его нет).
3. Проверить выравнивание первого кадра относительно позы покоя для презентации и прыжка;
   при подтверждённом смещении — поправить смещение отрисовки в `BimoPortrait`,
   не меняя графику.
4. Прогнать ещё раз весь перечень из п. 1, зафиксировать «до/после» скриншотами в PR.
5. Обновить `src/docs/profile-appearance.md`: какие таблицы точек появились, что

## Общие требования и приёмка

**Код:** TypeScript без `any`; алиасы `@/`; порядок импортов из `CLAUDE.md`; props через
`interface`; `'use client'` как можно глубже; Server Actions возвращают
`{ success: true, data } | { success: false, error }`; валидация входа через Zod `safeParse`;
после мутаций — `revalidatePath`/`revalidateTag`; серверные данные не хранить в `useState`;
клиентский кэш — только через `@/modules/cache`; оптимистичные обновления с откатом.

**Безопасность:** исход хода считает только БД; пользователь берётся из серверной сессии;
`fn_roulette_spin` и `fn_set_roulette_enabled` недоступны `anon`/`authenticated`;
секретов в коде нет.

**Документация:** создать `src/docs/roulette.md` по шаблону из `CLAUDE.md`
(логика, зависимости, типы, actions, queries, ограничения); обновить `src/docs/shop.md`
(новая вкладка), `src/docs/admin.md` (блок и выключатель в экономике),
`src/docs/profile-appearance.md` (этап 7). Перед этапом 1 обновить граф:
`/graphify . --update`.

**Проверки перед каждым коммитом:** `npx tsc --noEmit`, `npm run lint`, `npm run build`.
