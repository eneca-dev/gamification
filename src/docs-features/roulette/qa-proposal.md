Ответ MCP не является фиксированным лимитом счёта. По [правилам compute](https://supabase.com/docs/guides/platform/manage-your-usage/compute) начисление почасовое, неполный час округляется вверх; оплата использования — в конце текущего месячного billing cycle организации. Конкретная дата списания в инструментах не показана, нужна страница Billing владельца. Действующая подписка Pro остаётся общей, новую подписку на $25 для второго проекта не добавляем. Не вычитаем $10 org compute credits повторно: их свободный остаток не установлен.

Иллюстрация непрерывной работы без превышений, налогов и дополнительных услуг: 7 суток — $2.26, 14 — $4.52, 30 — $9.68. Это примеры, не выбранный срок и не согласованный бюджет. Compute не ограничивается Spend Cap. Дату остановки/удаления и бюджет выбирает пользователь; удаление потребует отдельного разрешения.

[Ветки](https://supabase.com/docs/guides/platform/manage-your-usage/branching) также оплачивают disk/egress/storage, не покрываются Spend Cap; compute credits для них не действуют. [Текущая схема создания веток](https://supabase.com/docs/guides/deployment/branching) подтверждает автоматическое воспроизведение миграций и перенос Edge Functions. Отсутствие данных в ветке не делает её безопасной для внешних отправок.

### Возможные доплаты

- [Disk](https://supabase.com/docs/guides/platform/manage-your-usage/disk-size): gp3 сверх 8 GB на проект — $0.125/GB-месяц.
- Общие квоты Pro уже расходует production. По [billing](https://supabase.com/docs/guides/platform/billing-on-supabase): uncached egress сверх квоты — $0.09/GB; Storage сверх квоты — $0.021/GB-месяц; Edge Functions сверх 2 млн вызовов — $2/млн; Realtime сверх 5 млн сообщений — $2.50/млн. Остатки квот пока не получены.
- [IPv4](https://supabase.com/docs/guides/platform/manage-your-usage/ipv4): $0.0055/час (~$4/месяц), **не включён**. Текущие гонковые тесты требуют прямой DB-host и IPv6. Если сеть его не поддерживает, сначала предложить session pooler с явной проверкой QA identity либо выполнение на доступном IPv6 runner; покупать IPv4 только отдельно.
- [PITR](https://supabase.com/docs/guides/platform/manage-your-usage/point-in-time-recovery): от ~$100/месяц, **не нужен и не включён**. Custom domain, реплики, более крупный compute, повышенные IOPS/throughput, платные логи — вне предложения.
- Налоги/валютная конвертация зависят от billing profile/банка; MCP их не рассчитал.
- Web hosting, туннель, дополнительные места/лимиты Airtable/Teams/Worksection не входят в $10. Тарифы соответствующих аккаунтов не проверены; новые покупки не предлагаются без конкретной цены.

## Конкретный состав QA

1. Один новый пустой Supabase-проект выше: собственные DB/Auth/Storage и ключи.
2. Приложение: сначала локальная **production-сборка** `npm run build && npm start` на рабочей машине, только с QA env. Дополнительный облачный хостинг на первом этапе не нужен. Для реального OAuth требуется разрешённый Worksection callback: подтвердить поддержку локального адреса либо предоставить существующий утверждённый HTTPS QA endpoint. Если понадобится новый туннель/деплой — отдельное предложение по цене до создания.
3. Изолированные сотрудники/покупатели и один администратор, отдельный товар для гонок, искусственные события/проводки/медиа. Реальных сотрудников, токены и production-данные не копируем.
4. Два тестовых Teams назначения (заказы/feedback), тестовая Airtable base/table и ограниченный PAT; Worksection sandbox/client с тестовыми сотрудниками. Существование этих ресурсов и свободные лицензии ещё не подтверждены.
5. Отдельный server-only `ROULETTE_CONFIRMATION_SECRET`; проверенные QA URL/публичный ключ/secret key; Playwright storageState отдельного сотрудника. Секреты передаются через локальные env/секрет-хранилище, не в чат или Git.

## Как получим безопасную исходную схему

1. Read-only snapshot **текущей схемы**, не последовательность исторических миграций: schema-only pg_dump совместимой версии или метаданные каталога. Для dump нужен read-only доступ к source DB; через MCP уже получены отдельные функции, но полного baseline ещё нет. Сохранить версию PG, extensions, объекты и хеши.
2. В локальном файле разобрать не только текст URL: DDL, defaults/generated expressions, RLS policies, triggers и транзитивно вызываемые функции, event triggers, FDW/dblink, pg_net/http, cron, vault references, SQL с динамическими вызовами, Edge Functions и внешние назначения. Schema-only dump тоже является исполняемым SQL и не запускается до review.
3. Из baseline исключить cron jobs/активации, Vault secrets, remote servers/user mappings, production URLs/ключи, HTTP-trigger подключения и непроверенные функции. Системные auth/storage схемы создаёт новый Supabase; их не заменять дампом production. Проверенные app policies/зависимости переносить явно. Состав исключений фиксируется, чтобы он не маскировал неполную функциональную приёмку.
4. Отдельным manifest описать Auth/Storage вне dump: custom access-token hooks/claims, соответствие тестовых Auth-пользователей синтетическим ws_users, admin-role, QA redirect allowlist, buckets/policies. Production настройки и секреты автоматически не копировать.
5. Подготовить отдельные `qa-baseline.review.sql`, список объектов/исключений и синтетический seed. Не вставлять фиктивные заглушки в проверяемые расчёты: реальные purchase/process_gamification_event и их зависимости обязательны. Подтвердить 9-аргументную live-сигнатуру начисления; старые миграции репозитория не являются источником истины.
6. Показать точный baseline + хеши до его применения. Только после отдельного согласования выполнить в выбранной QA-базе без внешних секретов/активных заданий; сверить функции, FK/UNIQUE, grants/RLS, BYN-trigger и отсутствие непроверенных исходящих вызовов. Повторять аудит после каждого изменения.
7. Подключать каждую реальную тестовую интеграцию отдельно после проверки адреса и разрешения. Активировать только нужное задание с тестовыми получателями. Доставка в mock не считается приёмкой.

## SQL: состав и порядок согласования

Точные локальные файлы — [sql/README.md](sql/README.md); SHA-256 — [sql/package-manifest.json](sql/package-manifest.json). Сейчас это содержательная версия для review, **не готовая команда применения**: QA ref и baseline ещё отсутствуют.

1. Безопасный baseline (пока не сформирован) и синтетический seed — отдельный пакет. Подготовить и проверить его до создания оплачиваемого проекта. После разрешённого применения — измерить исходные магазин/баланс/четыре RPC/экспорт на исходном HEAD до 01/02. Исходное приложение запускать из read-only архива HEAD в отдельной локальной папке, без checkout и без потери текущих изменений. По первому замеру согласовать допустимые регрессии.
2. `00-qa-marker.review.sql`: owner-only marker, оба допуска false. Placeholder намеренно вызывает отказ. Маркер не доказывает адрес подключения; ref проверяется отдельно по Dashboard и connection URL.
3. `01-roulette.review.sql`: журнал/одна delta-проводка/баланс, locks/replay, роли, default-off и production RNG/clock. `02-reporting.review.sql`: четыре согласованных RPC с проверкой исходных MD5. Рейтинг/история/spent не пересчитываются.
4. После отдельного утверждения QA-механизма и проверки исходящих назначений — выставить флаги marker и применить `03-qa-controls.review.sql`. Только QA, owner-only фиксирование времени/сектора, fixture-only fault injection.
5. Семь исходов, роли, реальные гонки/rollback и границы, а также детерминированные браузерные проверки сектора/месяца; затем `04-restore-production-helpers.review.sql` и тест реального RNG. Сохранить результаты и убедиться, что QA override удалён.
6. После удаления QA controls — обычные браузерные пути с реальными RNG/часами и повтор performance на тех же fixtures, ресурсах и cold/warm условиях. Для новой рулетки старого аналога нет: её latency измеряется отдельно, без выдуманного сравнения до/после. Полная v2.0-приёмка следует своей матрице. Любое применение в production остаётся отдельным будущим решением.

Четыре reporting RPC и расчёты: overview earned/factually_earned; top только earned; adoption core earned_total/earned_logged/earners; monthly earned_coins. Экспорт TypeScript: earned исключает только roulette, spent только отрицательные coins, все строки и полная сумма транзакций сохранены.
