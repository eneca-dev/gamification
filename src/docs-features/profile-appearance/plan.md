# Бимо: план гардероба и магазина v2

## Согласованные ограничения

- База: Supabase `yqezhfughtublpaitmij`; чтение и применение SQL только через MCP.
- Не менять существующие таблицы, функции, политики и данные. Разрешены новые таблицы, новые товары-черновики и две новые SQL-функции покупки/надевания (отдельно одобрены пользователем).
  Единственное последующее исключение: 2026-11-10 пользователь одобрил удаление
  неиспользованного черновика `accessory.blue_beanie` и его связи каталога.
  Удалено через MCP после проверки всех внешних связей, без изменения схемы.
- Черновик: одновременно `is_active=false` и `is_coming_soon=false`. Coming soon виден на витрине, использовать его нельзя.
- Админский интерфейс сейчас не менять. Коллекцию не публиковать до v2.
- Цена по обычной формуле `max(1, round(cost_byn * coefficient * current_crystal_rate()) + price_adjustment_crystals)`. 200 — начальный ориентир, не фиксированная цена.
- Браузер и компьютер пользователя не трогать для проверки интерфейса: пользователь тестирует самостоятельно.
- Git только на чтение. Исходники графики сохранять в игнорируемом `.local-assets/profile-appearance/`.
- Без агентов, временных таблиц и тестовых покупок в базе. Пользователь проверяет поведение самостоятельно после подключения интерфейса; сейчас разрешены проверка SQL и чтение метаданных/состояния.

## Порядок и прогресс — текущий согласованный план

База первоначально подготовлена 2026-11-05: две таблицы, 17 неактивных товаров
и две новые SQL-функции. На 2026-11-10 осталось 16 черновиков после явно
согласованного удаления синей шапочки. Все 16 имеют графику; публикация закрыта.
Итоговый состав, фактические проверки и ручные сценарии — в [графическом плане](artwork-plan.md).

«Код готов» означает реализацию с проверкой типов/сборки. Пользовательский путь в браузере ещё проверяет пользователь.

1. **Проверено.** Начатые серверные изменения: типы, запросы и ошибки.
2. **Код готов.** Обычная покупка запрещает обход операции Бимо: проверяются связь bimo_catalog и префикс эффекта. Обычная витрина исключает товары Бимо.
3. **Код готов.** Покупка вызывает новую SQL-функцию; пользователь берётся из серверной сессии.
4. **Код готов.** Надевание/снятие вызывает новую SQL-функцию, параметры проверяет Zod; неизвестная графика запрещена.
5. **Проверено на подставных данных.** Владение — fulfilled-заказ текущего пользователя без возврата.
6. **Проверено на подставных данных.** Эффективный образ требует точного source_order_id, пользователя, товара, действующего заказа, выпущенного каталога и поддержки графики; иначе базовый вариант.
7. **Код готов.** Существующие фабрики кеша инвалидируют bimo/balance/orders. Подписка на транзакции обновляет bimo; проверка повторяется при монтировании/фокусе. Новых подписок БД нет.
8. **Удалено по решению пользователя.** Страница /profile, ссылка, BimoLab и её специальные режимы удалены. Проверка продолжается в магазине.
9. **Код готов.** Общий BimoPortrait используется магазином и главной; лаборатория удалена.
10. **Проверено на подставных изображениях.** Кеш переиспользует загрузки, ограничен 5 изображениями и примерно 24 МиБ декодированных пикселей. Активный рендер и внутренний кеш браузера могут занимать больше.
11. **Код проверен; ручная проверка впереди.** Анимация конечная, рисует изменившийся кадр, останавливается при скрытии/размонтировании; reduced-motion оставляет портрет.

## Выпуск и доступность

- BIMO_V2_ENABLED в окружение не добавлялся; товары неактивны, is_released=false.
- Локально магазин Бимо виден при NODE_ENV=development. Просмотр черновиков не разрешает покупку. Тестовая страница /profile удалена полностью.
- В production базовый перетаскиваемый Бимо доступен на главной. Магазин/гардероб включается отдельным решением для v2 через серверный BIMO_V2_ENABLED=true и согласованную публикацию подготовленных товаров. Сам флаг товары не публикует.
- Успешная покупка, реальный возврат, конкурентные запросы и визуальный путь требуют ручной проверки в согласованной тестовой среде.

## Модель данных

`shop_products (цена, статус) → bimo_catalog (asset_key, slot, product_id, is_released=false)`

`shop_orders (владение) → bimo_equipment (user_id, slot, asset_key, source_order_id)`

Две бесплатные основы — классический костюм и мятный фон — значения по умолчанию в приложении, без покупки и отдельного товара. Пустой слот аксессуара означает отсутствие аксессуара.

16 платных черновиков: 4 костюма, 5 аксессуаров, 7 фонов. Список и постоянные ключи — в SQL; первоначальная синяя шапочка исключена отдельным `remove-blue-beanie-draft.sql`. Используется существующая категория `artifact`: она нефизическая и без ограниченного остатка. Визуальные разделы Бимо определяются `slot`, новая категория магазина не добавляется.

Первичный ключ `(user_id, slot)` запрещает несколько надетых вещей одного типа; составной внешний ключ проверяет соответствие вещи слоту. Операция надевания реализована новой SQL-функцией и серверным обработчиком. При чтении проверяются исходный заказ, пользователь, товар, статус и возврат. Недействительный выбор отображается как бесплатный базовый вариант. Второй копии инвентаря нет.

Новые таблицы: RLS включён; `anon` и `authenticated` не имеют доступа; серверный `service_role` имеет CRUD. Новые RPC — SECURITY INVOKER с фиксированным search_path; EXECUTE только у service_role и владельца. Серверные операции должны самостоятельно проверять сессию и владельца. Новые триггеры не добавляются; при установке функций покупки и списания не выполняются.

## Важные границы

Существующая RLS-политика `Authenticated users can read shop_products` допускает чтение всех товаров авторизованным клиентом через прямой API, включая черновики. Витрина фильтрует их по флагам; абсолютной секретности черновиков на уровне API нет. Для её изменения требуется отдельное разрешение на изменение существующей политики. В этом этапе она сохраняется.

`is_released` — дополнительный маркер выпуска каталога, проверяемый новыми функциями Бимо. Он сам по себе не меняет существующие SQL-функции покупки. Серверный путь уже подключён, но до ручной проверки и отдельного решения о выпуске товары остаются неактивными. Наличие графики не разрешает публикацию.

Товары сохраняют `image_url=NULL`, `media=[]`: графика в БД не хранится.
Постоянный `asset_key` связывает товар с файловым манифестом приложения.
Графика и отдельные превью всех 16 черновиков подготовлены; последние четыре
товара ещё требуют ручной визуальной проверки. Публикация отдельно не согласована.

## Контракт новых функций

- `purchase_bimo_item(p_product_id uuid, p_user_id uuid, p_user_comment text DEFAULT NULL)` возвращает прежние поля `order_id`, `status`, `coins_spent` плюс `asset_key`, `slot`.
- Только активный пользователь, выпущенная запись каталога и активный товар без coming-soon; активная категория `artifact` должна оставаться нефизической и неисчисляемой, effect должен совпадать с ключом каталога.
- Сначала блокируется строка товара. При стандартном READ COMMITTED следующий запрос видит завершившуюся конкурентную покупку. Иной уровень изоляции отклоняется (`bimo_requires_read_committed`). Каталог и категория защищены разделяемыми блокировками до конца транзакции.
- Любой неотменённый заказ без возврата блокирует повторное списание, включая pending/processing. Для надевания требуется именно fulfilled без возврата.
- Оплата вызывается через именованный текстовый аргумент `p_user_comment`: бесплатная перегрузка недоступна через новую функцию. Ошибка внутри старой покупки откатывает всю операцию.
- `equip_bimo_item(p_user_id uuid, p_slot text, p_asset_key text DEFAULT NULL)` возвращает `slot`, `asset_key`, `source_order_id`. Допустимы outfit/accessory/background. NULL удаляет выбор только в этом слоте.
- Изменения выбора сериализуются блокировкой строки пользователя. Источник владения — принадлежащий этому пользователю fulfilled-заказ нужного товара без возврата; строка заказа блокируется против одновременной отмены. Уже купленный снятый с продажи товар можно носить, если запись каталога остаётся выпущенной.
- Возврат, выполненный ПОСЛЕ надевания, может оставить строку выбора. Будущий запрос эффективного образа обязан повторно проверять пользователя/товар/fulfilled/refund/is_released и возвращать базовый образ при недействительном владении. Нельзя читать bimo_equipment и сразу отображать вещь без этих проверок. В серверной интеграции предусмотреть обновление данных после возврата.
- До публикации обязательно закрыть обход новой покупки через обычный серверный обработчик магазина: для товара из bimo_catalog или с эффектом `bimo:` использовать новый путь/отказать, не вызывать старую покупку напрямую. Все внутренние сервисные места покупки Бимо должны соблюдать это правило. Старые RPC сами по себе не проверяют повторное владение.
