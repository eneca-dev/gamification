# Переход Revit-плагинов на Plugins Usage Analytics (гибрид + переключатель на VPS)

Статус: **этапы 1–2 написаны (миграция 146 не применена; VPS-код не задеплоен, проверен dry-run), этап 3 частично, теневой период и релиз впереди**. Решения 30.10: без льготы, PartitionJoint/SpecLayout/LintelsCreator не добавляем, kibana.ts не трогаем. Данные анализа — окно 29.09–28.10.2026 (Минск). Заменяет раздел 5 из `src/docs/revit-plugin-usage-analytics.md` (тот документ остаётся как справочник по триггерам).

## Цель

После релиза v2.0 перевести часть плагинов с «запуска» (`App successfully started`) на «выполненное действие» из индекса `plugins-usage-analytics`, не потеряв плагины, которых в новом индексе нет. Для пользователя ничего не меняется в интерфейсе: те же дни, 💎, стрики, транзакции.

## Решения

1. **Гибрид.** 21 плагин, у которых в новом индексе есть результативные события, берём из аналитики; остальные (все Civil, SetToRevit, Evacuation, HVACAutoTag, SchedulesTable, ParkingSlots, LintelsTransfer, ClashesManager.Server) остаются на старых логах.
2. **Таблица для нового потока = теневая.** `elk_plugin_actions` — те же колонки, что у `elk_plugin_launches`, **без триггера**, никем не читается. Копится с первого деплоя, сверяется со старым потоком.
3. **Переключатель — константа `ANALYTICS_CUTOVER_DATE` в коде VPS** (`src/lib/plugin-analytics.ts`), не env: включение и откат идут коммитом в `main`, на сервере ничего менять не нужно. Для `work_date >= даты` строки аналитики дополнительно пишутся в **`elk_plugin_launches`**, а старый запрос исключает переведённые плагины. Триггер, транзакции, view стрика и все потребители таблицы не меняются. Дата — не раньше сегодняшней. Откат — вернуть `''` и запушить.
4. **Строка на пару «человек + плагин» за день, если было хотя бы одно результативное действие; `launch_count` = число запусков, внутри которых это действие было** (решение 02.11). Запуск определяется полем `Properties.Id` старых логов, связка с новым индексом — по точному времени события. Открытие без действия не создаёт строку и не попадает в счётчик. Отдельной метрики не вводим. Фильтра по активности сотрудника нет: как и раньше, неактивных отсекает только триггер начисления.
5. **Результативное событие** — любое, кроме явного denylist: старт, открытие/сбор настроек, смена вида, количественные дубли (`The number of spaces created`, `number of prototypes installed`, `ShareModel creation time`), `LoadFamily's`, отмена. Всего в индексе 95 различных `trigger`, ошибок среди них нет, отмена одна. Неизвестный `trigger` считается результативным и попадает в предупреждение Telegram.

## Почему `launch_count` считается через `Properties.Id`

В старых логах каждый запуск плагина имеет `Properties.Id`, общий для старта и всех событий этого запуска. Проверено по 19 плагинам за октябрь: поле заполнено у 100% документов, число уникальных Id совпадает с числом «App successfully started» 1:1 (SDT 3 992 и 3 991). Это точный разделитель запусков, без порогов и допущений.

Отвергнутые варианты:
- **склейка событий по паузе** — калибровка против эталона (10 603 запуска с действием за месяц) показала, что ни один порог не годится: ошибка по отдельным плагинам 35–66%, причём SDT (2 396 → 1 102 при 15 мин) и FasciaCappings (267 → 56) склеиваются, а ResaveModels (163 → 708 при 3 мин) и ClashesManager (246 → 567) разваливаются;
- **свой список полезных сообщений по старым логам** — расходится с кураторскими правилами в разы (у Кубышкиной EnecaFamilies 215 против 16), то есть это другое определение полезности, а не более точное;
- **все запуски за продуктивный день** — проще, но продолжает награждать за открытия: Пуссель получал 261 при 98 результативных.

Принято: определение полезного действия остаётся единственным (правила команды плагинов в новом индексе), а `Properties.Id` только группирует события в запуски. Связка точная — новый индекс построен из тех же логов и сохраняет `@timestamp`.

Сумма за октябрь (все плагины, активные): сейчас 20 654 → 15 246. Совпадение топ-10 достижения 6/10. Выпадают ровно те, кто много открывал без результата: Сергушов (1 061 → 37, место 1 → 99), Кубышкина (881 → 14, 2 → 188), Запрудский (506 → 4, 4 → 246), Иванова (274 → 108, 10 → 20). Это и есть цель достижения из `feature-2026-07-29`.

## Ожидаемый эффект (оценка, окно 30 дней)

- 155 из 278 теряют ≥1 зелёный день (у 28 — 5 и больше). Причины: ~33% старых запусков — «открыл без действия»; часть людей на версиях плагинов без аналитики (LinksManager 31 из 206, EnecaFamilies 42 из 175).

## Этапы

### Этап 1. БД (миграция)
- `elk_plugin_actions` (user_email, work_date, plugin_name, launch_count, synced_at; UNIQUE по трём первым; RLS включён, политик нет — читает только service_role).
- Правка `fn_award_revit_points`: при повторном UPDATE строки не дописывать дубль плагина в `details.plugins` (обновлять запись по `plugin_name`). Обязательно до переключения.
- Зависимости: нет. Проверка: повторный upsert строки не меняет `details.plugins` и не создаёт транзакцию.

### Этап 2. VPS (`gamification-vps-scripts`)
- `src/lib/plugin-analytics.ts`: список переведённых плагинов и маппинг имён (EnecaFamilies.Frontend/Backend → EnecaFamilies, Lookup Tables → LookupTables, ReSave Models → ResaveModels), denylist триггеров, `sessionize()`, константы.
- `sync-plugin-launches.ts`: читать события аналитики и запуски за минский день одним запросом без scroll (у кластера лимит 500 открытых scroll-контекстов; день, не влезший в 10 000 записей, — ошибка), проверка `timed_out` и `_shards.failed`, считать запуски с результатом, писать в `elk_plugin_actions`; при `work_date >= cutover` — ещё и в `elk_plugin_launches`, а старый запрос получает `must_not` по переведённым `AppName`.
- Заодно починить существующий запрос: пагинация composite по `after_key`, проверка шардов/таймаута, предупреждение при пустом ответе в будний день.
- Предупреждения (`warnings[]` в stats → Telegram): неизвестный `trigger`, новый `plugin_name`, email вне `ws_users`.
- Флаги: `--dry-run` (без записи), `--shadow-only` (только `elk_plugin_actions`), `--days=N` (бэкфилл; индекс хранит историю с 31.10.2024).
- Переключатель — константа `ANALYTICS_CUTOVER_DATE` в `src/lib/plugin-analytics.ts`, не env.
- **`launch_count` для переведённых плагинов** берётся из старых логов за ту же пару «почта + плагин + день», подтверждённую новым источником. Нужно только для рейтинга `fn_revit_launches_rank` (достижение «топ-10 по запускам»). Если запуска в старых логах нет (0,4% плагин-дней) — 1 и предупреждение.

## Риски

- В день переключения у людей без действия будет красный день → pending/щит. Продуктовое решение: льгота или нет.
- Поздние события (оффлайн-отправка логов) не попадут, если день уже синкнут; ручной догон — `--days=N`.
- Версии плагинов без аналитики дают ложные красные дни до обновления.
- Две системы единиц в одной таблице: до даты — запуски, после — операции (для переведённых плагинов).
