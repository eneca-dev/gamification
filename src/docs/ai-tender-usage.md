# Тендерные проекты в достижениях

Ночной VPS-скрипт `sync-ai-tender-usage` читает Elasticsearch и хранит не события, а дневные счётчики (по образцу `elk_plugin_launches`):

- `ai_tender_usage_daily`: одна строка на «проект + день по Минску + ключ пользователя + действие» с числом событий. Проекты: `advisor` (production `app_init` из `ai-tender-advisor-usage`) и `digest` (`tender.view`, `tender.decision`, `tender.create_lead` из `ai-tenderdigest-usage-prod*`). `tender.list` не считается использованием: загрузка списка может происходить при открытии страницы. Служебная учётка «Tender Adviser» в Digest пропускается.
- `tender_email_aliases`: единая таблица соответствий `(project, alias_key) → ws_user_id`. Для Adviser ключ — email из логов (рабочие адреса сотрудников там бывают другими, например `@eneca.by`), для Digest — числовой ID пользователя Digest (почты в логах нет).
- `ai_tender_usage_resolved`: представление, которое присоединяет сотрудника к счётчикам. Сопоставление считается при чтении, поэтому правка строки в `tender_email_aliases` сразу исправляет и прошлую статистику.

Скрипт сам создаёт недостающие строки соответствий: Adviser — по точному совпадению email с `ws_users`, Digest — по единственному совпадению полного имени. Существующие строки он не перезаписывает, поэтому ручные исправления сохраняются. Если сопоставить не удалось, `ws_user_id` остаётся пустым; такие пользователи видны в админке в блоке «Не сопоставлены с сотрудником» и не засчитываются никому. Исправление: заполнить `ws_user_id` в `tender_email_aliases`.

Все таблицы доступны только серверному ключу. Запросы личной статистики, если они используются вне `/achievements`, сопоставляют данные по `ws_user_id` пользователя, а не по его email.

Карточки Tender Adviser и Tender Digest удалены с `/achievements`; личные запросы статистики на этой странице не выполняются. На `/admin/achievements` по-прежнему доступны месячные итоги, сотрудники, разбивка по действиям и несопоставленные ключи.

`ai_tender_advisor_monthly` и `ai_tender_digest_monthly` имеют стоимость 200 кристаллов, но `is_active=false` и `create_transaction=false`. Сейчас собираются только счётчики и прогресс. Начисление, транзакции и изменение баланса потребуют отдельного включения после сверки данных.
